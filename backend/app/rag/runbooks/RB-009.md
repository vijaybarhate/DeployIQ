# RB-009 — Docker Image Build Failures

- **Runbook ID:** RB-009
- **Title:** Docker Image Build Failures
- **Affected technology:** Docker BuildKit, Dockerfile, build context
- **Risk level:** Low (blocks deployment; no runtime impact)

## Symptoms

- `docker build` / `docker compose build` exits non-zero; no image produced.
- Output names the failing step (`failed to solve`, `executor failed running [/bin/sh -c ...]`, `COPY failed: no such file`).
- Build checks (`docker build --check`) report lint violations; with `check=error=true` they fail the build.

## Possible causes

1. `COPY`/`ADD` referencing files outside the build context or missing from it (check `.dockerignore`).
2. Package install failure inside `RUN` (network, wrong package name, missing `--no-cache` staleness).
3. Wrong base image tag or architecture (`--platform` mismatch on ARM vs AMD64).
4. Dockerfile lint violations promoted to errors (`JSONArgsRecommended`, bad `CMD` shell form breaking signal handling).

## Diagnostic steps

1. Run `docker build --check .` first — fix reported violations before the real build.
2. Re-run with `docker --debug build .` — the annotated failing step and Dockerfile snippet pinpoint the line.
3. For `COPY` failures: list the build context and `.dockerignore` to confirm the source path is actually sent.
4. For `RUN` failures: reproduce the command in a throwaway container from the same base image.

## Verified remediation

- Fix the Dockerfile line (paths, package names, JSON-array `CMD`/`ENTRYPOINT` so signals propagate — shell form can swallow SIGTERM).
- Pin base image tags (`python:3.12-slim`, not `python:latest`) for reproducible builds.
- Keep `.dockerignore` tight so the context stays small and deterministic.

## Verification steps

- `docker build .` exits 0 with no check violations; `docker compose build` succeeds for all services.
- Fresh containers from the new image start cleanly (RB-001).

## DeployIQ notes (our recommendation, not vendor documentation)

- Build failures happen before any container exists, so the Docker collector sees no events — this runbook serves future CI log ingestion (Milestone 4), not the current event watcher.
