# RB-004 — Database Connection Failures

- **Runbook ID:** RB-004
- **Title:** Database Connection Failures
- **Affected technology:** Docker Compose networking, application database clients
- **Risk level:** Medium (app degraded; verify before restarting the database)

## Symptoms

- App logs show `connection refused`, `could not connect to server`, `Unknown MySQL server host`, `password authentication failed`, or timeouts on DB calls.
- DeployIQ evidence: `exception` category with connection error types, or HTTP 500s on DB-backed endpoints (see RB-007).
- The database container itself may be healthy — this is usually a reachability or credential problem, not a dead database.

## Possible causes

1. Wrong hostname: using `localhost` inside the app container (each container has its own localhost). On a Compose network the database is reachable by **service name** (e.g. `db`, not `localhost`).
2. App started before the database accepted connections (`depends_on` orders startup but does not wait for readiness).
3. Wrong credentials, database name, or port in the connection string (see RB-002).
4. Database container unhealthy or still initializing (large first-time init).

## Diagnostic steps

1. `docker compose ps` — is the `db` service `Up (healthy)` or still starting?
2. From the app container: `docker compose exec app getent hosts db` (or `ping db`) — confirms embedded-DNS name resolution.
3. `docker compose exec db <client> -U <user> -d <db> -c 'select 1'` — proves the database accepts connections independent of the app.
4. Compare the app's connection string host/port/user against the `db` service definition and its environment.
5. `docker logs db --tail 50` — look for `ready to accept connections` (Postgres) or equivalent.

## Verified remediation

- Point the app at the Compose service name, not `localhost`.
- Gate app startup on DB readiness: a `healthcheck` on `db` plus `depends_on` with `condition: service_healthy`, or a wait-for-it entrypoint wrapper.
- Fix credentials via environment (RB-002) and recreate the app service only — avoid restarting a healthy database.

## Verification steps

- The app's DB health endpoint (or a manual query through the app) succeeds.
- App logs show successful connection-pool initialization; DeployIQ incident stops growing.

## DeployIQ notes (our recommendation, not vendor documentation)

- Connection-refused tracebacks repeat identically on every request and deduplicate into one incident with a growing observation count — that is the expected signature, not runaway duplication.
