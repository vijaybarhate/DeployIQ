# RB-007 — Application HTTP 500 Errors

- **Runbook ID:** RB-007
- **Title:** Application HTTP 500 Errors
- **Affected technology:** Application code running in containers (any stack)
- **Risk level:** Medium (requests fail; container usually keeps running, so no Docker event fires)

## Symptoms

- Clients receive HTTP 500; container stays `Up` — `docker events` shows nothing (no `die`/`restart`).
- Container stderr contains a traceback ending in an exception line (e.g. `ZeroDivisionError: division by zero`).
- DeployIQ evidence: `exception` category with `exception_type`, `exception_message`, and `last_frame` (`file:line in function`).

## Possible causes

1. Unhandled application exception on the request path (bug, bad input, missing key).
2. Downstream dependency failure surfacing as a 500 (database, external API — see RB-004).
3. Misconfiguration loaded at request time (feature flag, missing file).

## Diagnostic steps

1. `docker logs <container> --tail 100 --timestamps` — capture the full traceback, not just the last line.
2. Read bottom-up: the final `ErrorType: message` line names the failure; the last `File "...", line N, in <func>` frame locates it.
3. Reproduce with a single request (`curl`) while tailing logs (`docker logs -f`) to isolate one traceback from concurrent traffic.
4. Check whether the 500 correlates with a dependency: same timestamp errors in the `db`/API containers.

## Verified remediation

- Fix the code path or input validation; add a regression test for the failing input.
- Return 4xx for client-caused bad input instead of letting it raise to a 500.
- Fix or time out the downstream dependency if the traceback ends in a client call.

## Verification steps

- The reproducing request returns the expected status; no new traceback in `docker logs`.
- DeployIQ incident for the signature stops growing (observation count flat).

## DeployIQ notes (our recommendation, not vendor documentation)

- HTTP 500s produce no Docker event, so our collector tails stdout/stderr (`since` + per-line identity) to catch them. Identical tracebacks deduplicate into one incident; `matched_line_count` counts the extracted error lines per observation.
