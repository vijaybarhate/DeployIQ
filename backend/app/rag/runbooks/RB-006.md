# RB-006 — Docker Health Check Failure

- **Runbook ID:** RB-006
- **Title:** Docker Health Check Failure
- **Affected technology:** Dockerfile `HEALTHCHECK`, Compose `healthcheck`, Docker Engine
- **Risk level:** Medium (orchestrators treat `unhealthy` as failed; app may still serve traffic)

## Symptoms

- `docker compose ps` shows the service `Up (unhealthy)`.
- `docker events` shows `health_status: unhealthy` for the container.
- App may still respond on some routes — unhealthy means the *check command* failed, not necessarily a dead process.
- DeployIQ evidence: `health` category incident (`<service> unhealthy`).

## Possible causes

1. The checked endpoint regressed (returns 500) while the rest of the app works — check too narrow or app partially broken.
2. `HEALTHCHECK` command itself broken (missing tool in image, e.g. no `curl`; wrong port/path).
3. Interval/timeout/retries too aggressive for a slow-starting app (no or short `start-period`/`start_period`).
4. Dependency the endpoint needs (database) is down while the app process lives.

## Diagnostic steps

1. Run the exact check command manually: `docker compose exec <service> <test-command...>` — reproduce the failure.
2. `docker inspect <container> --format '{{json .State.Health}}'` — read the failing output and consecutive-failure count.
3. Hit the endpoint from outside the healthcheck path and compare (is it the endpoint or the probe?).
4. Review `interval`, `timeout`, `retries`, `start_period` in the Compose file/Dockerfile against actual startup time.

## Verified remediation

- Fix the app endpoint or the probe command (use tools present in the image; `python -c "import urllib.request..."` needs no `curl`).
- Give slow starters a `start_period` covering worst-case init, and keep `retries` ≥ 2 to ride out single blips.
- If the endpoint depends on a database, fix the database path (RB-004) rather than deleting the check.

## Verification steps

- Status transitions `unhealthy → healthy` (allow `interval × retries` plus start period).
- `docker inspect` health log shows `exitCode: 0` on recent checks; DeployIQ health incident stops growing.

## DeployIQ notes (our recommendation, not vendor documentation)

- A `health_status: unhealthy` daemon action arrives with a status suffix (`health_status: unhealthy`), not a bare action name — event filters must split base action from status. Health state changes carry no exit code, so they are classified from the event itself, not from logs.
