# RB-003 — Port Binding Conflicts

- **Runbook ID:** RB-003
- **Title:** Port Binding Conflicts
- **Affected technology:** Docker Engine networking, Docker Compose `ports`
- **Risk level:** Low (startup blocker; no data risk)

## Symptoms

- `docker compose up` fails for one service with: `Bind for 0.0.0.0:<port> failed: port is already allocated`.
- The container never reaches `running`; no application logs exist (failure happens before the process starts).
- DeployIQ evidence: container `create`/`start` attempted, then immediate `die`, or the service missing from `docker compose ps`.

## Possible causes

1. Another container (or host process) already publishes the same host port.
2. A previous copy of the same stack is still running (`compose down` was never run).
3. Port range collision after changing `ports:` mappings.

## Diagnostic steps

1. Read the exact daemon error — it names the conflicting host port.
2. `docker ps --format '{{.Names}}\t{{.Ports}}'` — find which container holds the port.
3. On the host: check for non-Docker listeners on the port (e.g. a local dev server).
4. `docker compose -p <other> ps` — check for a second stack with the same mapping.

## Verified remediation

- Stop the stale holder (`docker compose down` in the old project directory, or stop the host process), or
- Remap the host side in Compose (`"18000:8000"` instead of `"8000:8000"`) and `docker compose up -d`.
- Use `-p` published ports only where external access is needed; container-to-container traffic on the same user-defined network needs no published port (containers reach each other by service name via the embedded DNS server at `127.0.0.11`).

## Verification steps

- `docker compose ps` shows the service `Up` with the expected `0.0.0.0:<port>->...` mapping.
- The endpoint responds from the host (`curl localhost:<port>`).

## DeployIQ notes (our recommendation, not vendor documentation)

- Port conflicts fail before the app logs anything, so expect event-only evidence (`create`/`die`) with empty log tails — a normal pattern, not collector malfunction.
