# RB-001 — Docker Container Startup Failure

- **Runbook ID:** RB-001
- **Title:** Docker Container Startup Failure
- **Affected technology:** Docker Engine, Docker Compose
- **Risk level:** Medium (service outage until resolved; changes are diagnostic-only)

## Symptoms

- `docker compose up` or `docker run` exits immediately; `docker ps` shows no running container.
- `docker ps -a` shows the container with status `Exited (1)` or another non-zero code seconds after start.
- DeployIQ evidence: `exit_code` category, or `die` event with non-zero `exitCode` and no preceding `kill` event.
- A fresh `docker logs <container>` shows an error within the first lines (missing file, bad command, import error).

## Possible causes

1. Wrong `CMD`/`ENTRYPOINT` (binary not found, bad arguments).
2. Missing files or volumes at the expected mount path.
3. Application crash during initialization (bad config, missing dependency).
4. Image pull failure or wrong image tag (container never actually starts the app).

## Diagnostic steps

1. `docker ps -a --filter "name=<name>"` — confirm `Exited (<code>)` and how long ago.
2. `docker logs <container> --tail 100` — read startup output from the beginning; the first error line is usually the cause (see RB-007 for traceback reading).
3. `docker inspect <container> --format '{{.Config.Cmd}} {{.Config.Entrypoint}}'` — verify the executed command.
4. `docker events --since 10m --filter container=<name>` — confirm the sequence is `create → start → die` with no `kill` in between (a `kill` first means an operator/orchestrator stopped it — see RB-008).
5. Reproduce with `docker compose up <service>` in the foreground to see interleaved output.

## Verified remediation

- Fix the underlying command, path, or image tag in the Compose file / Dockerfile and recreate: `docker compose up -d --force-recreate <service>`.
- Do not paper over startup crashes with `restart: always` — a container that cannot start will only restart-loop (the daemon restarts it after it stays up <10s only once monitored; a crash-loop still pages).

## Verification steps

- `docker compose ps` shows the service `Up` for longer than the previous crash interval.
- `docker logs <container> --tail 20` shows the application's ready message, not a traceback.
- DeployIQ: no new incident for the service after recreate.

## DeployIQ notes (our recommendation, not vendor documentation)

- A `die` event with exit `1` and no prior `kill` is treated as an unexpected exit (incident). A `die` shortly after `kill` (SIGTERM/SIGINT) is treated as a planned stop. This distinction is what keeps `compose down` from paging.
