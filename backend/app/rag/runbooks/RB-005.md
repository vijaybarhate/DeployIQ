# RB-005 — Container OOMKilled

- **Runbook ID:** RB-005
- **Title:** Container OOMKilled
- **Affected technology:** Docker Engine memory limits, Linux cgroups, kernel OOM killer
- **Risk level:** High (abrupt termination, possible data loss on in-flight work)

## Symptoms

- Container shows `Exited (137)`; `docker events` shows an `oom` event followed by `die` (exit 137).
- Logs end abruptly with no traceback; the kernel message `Killed process ...` / `out of memory` may appear on the host (`dmesg`), not in container logs.
- DeployIQ evidence: `oom` category (or `die` with exit 137 correlated to a recent `oom` event).

## Possible causes

1. No memory limit set and the app leaks or spikes beyond host capacity — the kernel OOM killer picks the container.
2. Memory limit (`-m`/`--memory`, Compose `mem_limit`) set below the app's working set.
3. Memory plus swap accounting misunderstood (`--memory-swap` semantics).
4. Load spike (traffic, batch job, large import) exceeding the normal footprint.

## Diagnostic steps

1. `docker events --since 30m --filter event=oom` — confirm the kernel actually OOM-killed (vs a manual `kill -9`, which also exits 137 — see RB-008).
2. `docker inspect <container> --format '{{.HostConfig.Memory}}'` — check the configured limit (0 = unlimited).
3. `docker stats --no-stream` — observe current footprint vs limit.
4. Host `dmesg | grep -i "out of memory"` — find which process the kernel killed and its score.
5. Profile the app under load to separate a leak (grows unboundedly) from a spike (returns to baseline).

## Verified remediation

- Set an explicit limit sized from measurements, e.g. Compose `mem_limit: 512m` with `memswap_limit` understood per the `--memory-swap` rules (equal values disable swap).
- Fix the leak or cap the spike (worker concurrency, batch size, streaming instead of buffering).
- Do not set `--oom-kill-disable` unless a hard limit is also set — otherwise the host itself can OOM.

## Verification steps

- Re-run the previous workload: no `oom` event, container stays up, `docker stats` stays under the limit.
- DeployIQ: no new OOM incident for the service.

## DeployIQ notes (our recommendation, not vendor documentation)

- Exit 137 alone is ambiguous, so our collector correlates the full event sequence: `kill` SIGTERM/SIGINT (signals `15`/`2`) followed by `die` is a planned stop, including when the daemon SIGKILLs after the grace period; a standalone `kill` with signal `9` (SIGKILL, no preceding stop request) stays an incident; `die(137)` after an `oom` event merges into the OOM incident.
