# RB-008 — Unexpected Container Exits

- **Runbook ID:** RB-008
- **Title:** Unexpected Container Exits
- **Affected technology:** Docker Engine events, exit codes, restart policies
- **Risk level:** High (service down; distinguish crash from planned stop before acting)

## Symptoms

- `docker ps -a` shows `Exited (<non-zero>)`; the service is down.
- `docker events` shows `die` with an `exitCode` attribute.
- DeployIQ evidence: `exit_code` category (`exit code N`), possibly merged with `exception` evidence if the logs contain a traceback.

## Possible causes

1. Application crash (see RB-001, RB-007).
2. OOM kill — exit 137 with a preceding `oom` event (see RB-005).
3. Manual `docker kill -9` — exit 137 preceded by a `kill` event with `signal=9` and nothing else (standalone SIGKILL with no preceding SIGTERM/`stop` and no `oom`). **An incident.**
4. Operator/orchestrator stop — `kill` (SIGTERM/SIGINT, signal `15`/`2`) then `die` (143, or 137 if SIGKILL followed the grace period), or clean exit 0. **Not an incident.** `docker stop` sends SIGTERM first and SIGKILLs only if the grace period expires.

## Diagnostic steps

1. `docker events --since 15m --filter container=<name>` — reconstruct the exact sequence: `kill`? `oom`? bare `die`?
2. Map the exit code: `0` clean · `1` app error · `130` SIGINT · `137` SIGKILL/OOM · `143` SIGTERM · `139` SIGSEGV.
3. `docker logs <container> --tail 100` — traceback present means crash-with-evidence; absent abrupt end means kill/OOM (check `oom` event and host `dmesg`).
4. `docker inspect <container> --format '{{.HostConfig.RestartPolicy}}'` — know whether the daemon will restart it.

## Verified remediation

- Crash/OOM/manual-kill: fix the underlying cause (RB-001/RB-005/RB-007), then `docker compose up -d`.
- Planned stops need no remediation — but confirm the stop was intended (`compose down` vs an unexpected orchestrator drain).
- For crash-prone services, set `restart: unless-stopped` (or `on-failure`) so the daemon restarts them; still investigate the incident, since restart policies mask root causes.

## Verification steps

- Service `Up` and stable; `docker events` shows `start` with no follow-up `die`.
- DeployIQ: no new exit incident for the service.

## DeployIQ notes (our recommendation, not vendor documentation)

- Our collector classifies `die` by correlating signals: `0` always clean; `143/130` only planned after a recorded `stop`/`kill`; `137` after `kill` SIGTERM is a planned stop (grace-period SIGKILL), `137` after `oom` merges into the OOM incident, lone `137` stays an incident. Event action `health_status: unhealthy` carries a status suffix that must be split from the base action.
